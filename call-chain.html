端對端展示從前端操作、Hono 路由、Service 狀態機、Repository 交易到 D1 SQLite 資料庫與 Web Push 的完整生命週期調用鏈。

1
領取者 POST Google / Dev 登入授權
/api/auth/google & /api/auth/dev-login

使用者按 Google 官方登入按鈕（彈窗模式），前端把 credential 當作 idToken 送到 POST /api/auth/google。後端以 jose 用 Google JWKS 驗證 ID Token，通過後簽發 HttpOnly Cookie。本機開發（ENVIRONMENT 為 development）可改用 POST /api/auth/dev-login 的開發者模擬登入，其他環境該路由回應 403。

調用方法 (Service & Repo)
AuthService.loginWithGoogle() (先 verifyGoogleIdToken，以 jose 驗證 Google ID Token) 或 loginWithDevAccount() ➔ UserRepository.upsertUserByGoogleProfile() ➔ AuthService.createSessionToken() (hono/jwt)
資料庫與狀態變更 (D1 SQLite)
SELECT users WHERE google_sub = ? ➔ 不存在: INSERT INTO users (google_sub, email, nickname, ...) ➔ 已存在且 email 或暱稱有變: UPDATE users ➔ Set-Cookie: claude_tw_session=eyJhbGci...
2
領取者 POST 加入排隊並預填感謝小卡 (AC 1)
/api/queue

領取者排隊時需預先撰寫 5~200 字感謝小卡（確認啟用時將刊登至感謝牆）。前端依 isEligibleForNewbieTrack 自動送出排隊軌道，畫面沒有軌道選項。若此時池中無可配對的名額，狀態為 waiting。

調用方法 (Service & Repo)
InviteQueueService.joinQueue() ➔ processExpirations() (先結算逾時) ➔ resolveJoinTrack() (省略 track 時依資格自動分軌；明確要求 newbie 但不具資格才拒絕) ➔ InviteQueueRepository.createQueueEntry() ➔ InviteQueueService.matchAvailableSlotsToQueue()
資料庫與狀態變更 (D1 SQLite)
INSERT INTO queue_entries (user_id, status='waiting', track, priority=0, thank_you_message) ➔ 初始狀態: waiting (排隊順位: N) ➔ 池中有可配對的名額時，同一個請求內即轉為 reserved
💡 業務防重防護：同一個使用者在狀態為 waiting, reserved, revealed 時無法重複排隊（唯一索引違反時回傳 ALREADY_IN_QUEUE）。新手首發軌另外限制：任一軌道已有 confirmed 紀錄，或曾分享過邀請連結的使用者，請求明確帶 newbie 時回傳 NEWBIE_TRACK_ONLY，需改排再領取軌；請求省略 track 時，這類使用者直接排再領取軌。
3
提供者 POST 分享邀請連結並觸發自動配對 (AC 2, AC 3)
/api/links

提供者分享包含代碼的網址（自訂 1~3 名額，並選擇名額開放給新手首發軌或再領取軌），系統原子交易寫入名額並立即依軌道規則按 FIFO 撮合給排隊者。

調用方法 (Service & Repo)
InviteQueueService.submitInviteLink() ➔ rules.extractAndNormalizeReferralLink() ➔ processExpirations() (先結算逾時) ➔ UserRepository.findUserById() ➔ rules.isProviderBlocked() ➔ InviteQueueRepository.createLinkWithSlots() (D1 Batch) ➔ InviteQueueService.matchAvailableSlotsToQueue()
資料庫與狀態變更 (D1 SQLite)
BEGIN BATCH INSERT INTO invite_links (...) INSERT INTO invite_slots (status='available', track) * N COMMIT ➔ 撮合後: slot: reserved, queue: reserved
🔔 即時通知觸發：配對成功的領取者收到 Web Push（「輪到你領取 Claude 邀請碼」，內文提醒請在 6 小時內點擊解鎖）。推播交給 runInBackground（Workers 的 ctx.waitUntil）在回應之後送出，不拖慢 API 回應。
4
領取者 POST 解鎖看碼 (AC 4, AC 6)
/api/queue/reveal

在 6 小時保留期內尚未解鎖時，GET /api/me 的 myQueue.referralUrl 為 null；領取者點擊解鎖後，POST /api/queue/reveal 才回傳邀請網址，並啟動 30 分鐘啟用倒數窗口。

調用方法 (Service & Repo)
InviteQueueService.revealSlot() ➔ processExpirations() (先結算逾時；已逾期者回傳 RESERVATION_EXPIRED) ➔ InviteQueueRepository.revealReservedSlot() (D1 Batch，WHERE reserve_expires_at > now) ➔ InviteQueueRepository.findSlotWithLinkById() (取得邀請網址)
資料庫與狀態變更 (D1 SQLite)
UPDATE invite_slots SET status='revealed', confirm_expires_at=now+30m UPDATE queue_entries SET status='revealed', confirm_expires_at=now+30m ➔ 狀態轉變: revealed (顯示倒數計時)
5
領取者 POST 確認啟用並送出感謝 (AC 6)
/api/queue/confirm

領取者在 Claude.ai 註冊啟用成功後，點擊「確認啟用並送出感謝」，名額結案，感謝小卡以背景推播送給提供者，並在看板快取更新後刊登至首頁感謝牆。

調用方法 (Service & Repo)
InviteQueueService.confirmSlot() ➔ InviteQueueRepository.confirmRevealedSlot() ➔ notifyProviderOnSlotConfirmed() ➔ syncProviderStrikeCount() ➔ dispatchPush() ➔ WebPushService.sendNotificationToUser(providerId) (背景送出) ➔ onSlotConfirmed()，即 invalidateBoardAndTotalConfirmedCount() (清本 isolate 的看板快取與 totalConfirmedCount 快取)
資料庫與狀態變更 (D1 SQLite)
UPDATE invite_slots SET status='confirmed', confirmed_at=now UPDATE queue_entries SET status='confirmed', confirmed_at=now ➔ 狀態結案: confirmed ➔ 同一個請求內清除本 isolate 的看板快取 ➔ 其他 isolate 的快取最多 15 秒後過期，之後的讀取才在感謝牆顯示此張小卡與雙方暱稱
⏰
系統排程 Cron Cron Trigger 定時排程檢查 6 小時未解鎖名額 (AC 5)
wrangler.toml: crons = ["*/5 * * * *"]

逾時結算有四種觸發時機：每 5 分鐘執行的 scheduled()、登入狀態的 GET /api/me、看板快取過期後的 GET /api/board，以及提交連結、加入排隊、取消、解鎖、回報無效這幾支寫入 API（確認啟用不會先結算）。結算時掃描所有 status = 'reserved' 且 reserve_expires_at <= now 的排隊紀錄（每次最多 100 筆），並以同樣上限掃描 status = 'revealed' 且 confirm_expires_at <= now 的排隊紀錄，自動確認啟用。

調用方法 (Service & Repo)
InviteQueueService.processExpirations() ➔ InviteQueueRepository.fetchExpiredReservations() 與 fetchExpiredRevealedSlots() (同時查詢) ➔ InviteQueueRepository.expireReservationAndReleaseSlot() (逐筆) ➔ confirmRevealedSlot() (逐筆，解鎖滿 30 分鐘自動確認) ➔ 每筆自動確認成功後，馬上背景推播通知提供者 ➔ syncProviderStrikeCount() (受影響的提供者) ➔ 有逾時釋出的名額時: matchAvailableSlotsToQueue() ➔ 清快取: 有自動確認時 onSlotConfirmed()，只有逾時釋出時 onBoardChanged()
資料庫與狀態變更 (D1 SQLite)
UPDATE queue_entries SET status='expired', slot_id=null WHERE id=? UPDATE invite_slots SET status='available', assigned_user_id=null ➔ 原領取者逾時標記為 expired；名額退回 available（同一組連結已有名額被回報無效時改為 closed）
🔄
系統排程 Cron BATCH 釋放名額立即自動撮合下一位等待者 (AC 5)

名額退回 available 後，系統不浪費名額，立即調用配對引擎，依軌道規則將名額保留給佇列中的下一位排隊者。

調用方法 (Service & Repo)
InviteQueueService.matchAvailableSlotsToQueue() (最多 5 輪) ➔ fetchTracksWithWaitingEntries() ➔ fetchAvailableSlotsForMatching() ➔ fetchWaitingQueueEntriesForMatching() (每軌用 ROW_NUMBER() 取前 N 張票券) ➔ matchTicketsToAvailableSlots() (domain 純函式) ➔ InviteQueueRepository.assignSlotToQueueEntry() ➔ dispatchPush() ➔ WebPushService.sendNotificationToUser(nextUserId) (背景送出)
資料庫與狀態變更 (D1 SQLite)
UPDATE invite_slots SET status='reserved', assigned_user_id=nextUserId, reserve_expires_at=now+6h UPDATE queue_entries SET status='reserved', slot_id=?, reserve_expires_at=now+6h ➔ 兩筆 UPDATE 在同一個 D1 Batch，各自帶 WHERE status 守衛 ➔ 下一位等待者晉升為 reserved，收到推播領取通知
⚠️
領取者 POST 回報邀請碼無效 (AC 8, AC 9, AC 10)
/api/queue/report-invalid

領取者解鎖看碼後發現無法註冊（如已被他人搶用），在 30 分鐘窗口內點擊回報無效。

調用方法 (Service & Repo)
InviteQueueService.reportSlotInvalid() ➔ processExpirations() (先結算逾時) ➔ 檢查是否已用過終身 1 次重排額度 (RETRY_QUOTA_EXHAUSTED) ➔ rules.canUserReportInvalid() (解鎖後 30 分鐘內) ➔ InviteQueueRepository.reportInvalidAndRequeue() (D1 批次交易，4 條語句) ➔ syncProviderStrikeCount() ➔ matchAvailableSlotsToQueue()
D1 4 條語句原子批次交易 (Batch Transaction)
BEGIN BATCH 1. UPDATE invite_slots SET status='invalidated' WHERE id=? 2. UPDATE invite_slots SET status='closed' WHERE link_id=? AND status='available' (同組隔離) 3. UPDATE users SET invalid_retry_count=invalid_retry_count+1 WHERE id=? (扣除重排額度) 4. UPDATE queue_entries SET status='waiting', priority=1 WHERE id=? (優先插隊，軌道不變) COMMIT
🛡️
系統自動防護 EVAL 好心人保護與累積 2 次停權判定 (AC 10)

系統重新評估提供者所有連結的健康度：只要任一名額曾成功啟用，即不判定為完全無效連結；累積 2 組全無效則自動停權。

調用方法 (Service & Repo)
InviteQueueService.syncProviderStrikeCount() ➔ InviteQueueRepository.fetchProviderLinksSlotStatuses() ➔ rules.isCompletelyInvalidLink(statuses) ➔ UserRepository.updateProviderStrikeCount() ➔ rules.isProviderBlocked(strikeCount) (reportSlotInvalid 取得回傳值後判定並記錄)
判定結果
strikeCount >= 2 ➔ 提供者被停權，後續 POST /api/links 回應 HTTP 403 PROVIDER_BLOCKED
⚡
80 併發領取者 CONCURRENT POST 同時排隊搶名額與守衛條件撮合
tests/stress/concurrency.stress.test.ts

壓力測試先讓 20 位提供者各提交一組 3 個名額的連結（共 60 個名額），再用 Promise.all 讓 80 位領取者同時 POST /api/queue。測試用 better-sqlite3 模擬 D1，並在每次 D1 存取前依固定種子讓出事件迴圈 1 到 4 次（共 6 組種子），讓請求在「讀可用名額」與「寫入配對」之間交錯。配對被別的請求搶先時，守衛條件使該筆寫入落空，撮合迴圈重讀後再配，最多 5 輪。

並發競爭調用鏈
Promise.all(80 * POST /api/queue) ➔ matchAvailableSlotsToQueue() (最多 5 輪) ➔ 每輪先查有 waiting 票券的軌道，只讀配得到的軌道的 available 名額， 再每軌用 ROW_NUMBER() 取前 N 張票券 ➔ InviteQueueRepository.assignSlotToQueueEntry() (D1 batch()) ➔ 兩條 UPDATE 的 WHERE 各帶 status 守衛與 EXISTS: 名額: WHERE id=? AND status='available' 排隊紀錄: WHERE id=? AND status='waiting' ➔ 任一筆未影響 1 列即視為被拒絕，下一輪重讀再配
測試斷言的不變性 (Invariant)
✓ 剛好 60 個名額與 60 筆排隊紀錄為 reserved，available 名額為 0 ✓ 剛好 20 筆排隊紀錄為 waiting (不交錯的那條測試另外檢查 GET /api/me 的排隊順位恰為 1~20) ✓ 0 個名額被兩筆排隊紀錄占用 (Zero Double-Allocation) ✓ reserved 的名額與排隊紀錄互相對應 (assigned_user_id 與 slot_id 一致)

🔒 邀請網址的可見範圍

排隊紀錄的 referralUrl（GET /api/me 的 myQueue 與 myConfirmedClaim）只在狀態為 revealed 或 confirmed 時有值，其餘狀態為 null。提供者自己分享的連結網址一直顯示在 mySharedLinks[].normalizedUrl。

📦 D1 Batch 原子交易

跨表狀態轉移（如配對、回報無效同組隔離）全面使用 D1 Batch，確保多表要嘛全成、要嘛全敗，零部分寫入殘留。

🧪 壓力測試涵蓋範圍

tests/stress/concurrency.stress.test.ts 以 better-sqlite3 模擬 D1，驗證 80 位領取者搶 60 個名額後的資料一致性。scripts/http-load-test.mjs 對 localhost:8787 的本機 Worker 送出真實 HTTP 請求（30 位登入、5 位提供者提交共 15 個名額、25 位領取者排隊、獲配者解鎖並確認），只在執行時印出各階段耗時與 req/s。
