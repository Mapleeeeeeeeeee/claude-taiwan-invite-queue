🛡️ 接入與中介層 (API Gateway & Middleware Layer)
Hono v4 輕量路由 + 安全防護標頭 + Zod 輸入強驗證
secureHeaders() Security
對 /api/* 注入 HSTS, X-Frame-Options (SAMEORIGIN), X-Content-Type-Options (nosniff) 與 Referrer-Policy (no-referrer)，皆為 Hono 預設值。
Session 中介層 Auth
app.use('/api/*') 每個請求建立一次 createServices()，解析 claude_tw_session JWT Cookie 並把 userId（未登入或驗證失敗為 null）放進 Context；需要登入的路由再由 requireUserId() 回傳 401。
zValidator() Validation
Zod 綱要檢查（感謝小卡長度 5~200 字、名額 1~3、軌道 newbie／community、推播訂閱欄位），失敗回傳 422 VALIDATION_ERROR；登入相關欄位失敗回傳 400 INVALID_INPUT。
app.onError() Error Boundary
統一捕捉業務 AppError 並轉成 { error: { code, message } }；非預期錯誤只回傳通用的 500 INTERNAL_ERROR，細節寫入 log，不洩漏給使用者。

POST /api/queue/report-invalid 回報代碼無效 (同組隔離、提供者扣點、priority=1 優先重排)
需登入 (Cookie) 終身限 1 次
Service inviteQueueService
reportSlotInvalid(userId, now) 1. 先 processExpirations(now) 結算逾時；沒有任何排隊紀錄回傳 404 QUEUE_ENTRY_NOT_FOUND。
2. 排隊紀錄已 confirmed：回傳 409 CONFIRM_WINDOW_EXPIRED。

reportInvalidAndRequeue() [原子交易] 1. 將當前名額標為 invalidated。
2. 同組名額隔離：關閉該連結所有仍處於 available 的名額 (標為 closed)，避免其他版友踩雷；已配給他人的 reserved 名額不受影響。
3. 領取者 invalid_retry_count + 1。
4. 領取者重新入隊，標記 priority = 1（插隊優先權），軌道維持原樣。

1. 名額 (Slot) 完整狀態轉移流 (Slot State Machine)

追蹤從提供者釋出名額到最終兌現或回收的嚴格有限狀態流：

[建立釋出] │ ▼ AVAILABLE ──(撮合引擎 matchTicketsToAvailableSlots)──► RESERVED (6 小時保留看碼窗口) │ │ │ (同組無效隔離) ├──(逾時 6h 未解鎖 或 領取者放棄保留)──► AVAILABLE，立即重新撮合 (同連結已有 INVALIDATED 名額時改為 CLOSED) ▼ │ CLOSED └──(領取者點擊解鎖)──► REVEALED (30 分鐘啟用窗口) │ ├──(滿 30 分鐘或點擊確認)──► CONFIRMED (感謝上牆、推播) │ └──(回報無效)──► INVALIDATED (同組可用關閉、記點)
2. 領取者排隊紀錄 (QueueEntry) 狀態流 (Queue Entry State Machine)

追蹤領取者加入隊列至成功啟用或重排的生命週期（每筆排隊紀錄屬於 newbie 或 community 其中一個軌道）：

[加入排隊 POST /api/queue] │ ▼ WAITING (順位計算 queuePosition，所有軌道合併 FIFO) │ ├──(使用者手動取消)──► CANCELLED │ ▼ (撮合引擎指派) RESERVED (隱蔽邀請碼，通知領取者) │ ├──(使用者放棄保留)──► CANCELLED (名額釋出並重新撮合) │ ├──(逾時 6 小時未解鎖)──► EXPIRED (名額釋出，領取者可重新在隊尾排隊) │ ▼ (解鎖看碼 POST /api/queue/reveal) REVEALED (顯示 referralUrl，啟動 30 分鐘倒數計時) │ ├──(點擊確認 或 30 分鐘到期)──► CONFIRMED (兌現終態，獲得邀請碼；不能再排新手首發軌，但可改排再領取軌) │ ▼ (回報無效 POST /api/queue/report-invalid) WAITING (priority = 1 插隊優先重排，軌道不變，僅限 1 次機會)
3. 定時與延遲結算週期 (Lazy Expiration Engine)

Workers 上沒有常駐程序，逾時名額由 Cron Trigger 與「請求延遲結算」兩種機制共同結算：

  • 觸發時機：processExpirations(now) 有四種觸發時機。一是 wrangler.toml 的 crons = ["*/5 * * * *"]，每 5 分鐘由 scheduled() 執行；二是登入狀態的 GET /api/me；三是 GET /api/board 在看板快取（15 秒）過期時；四是提交連結、加入排隊、取消、解鎖、回報無效這幾支寫入 API 在處理前先結算。確認啟用的 API 不會先結算。
  • 6 小時保留逾時清理：尋找 queue_entries.status = 'reserved' AND reserve_expires_at <= now（每次最多 100 筆）。將 queue entry 標為 expired，並將 slot 退回 available（同連結已有 invalidated 名額時改為 closed）；有名額釋出時再呼叫 matchAvailableSlotsToQueue()，依軌道規則重新自動配對給下一位等候者，無人等候則維持 available。
  • 30 分鐘自動確認結算：尋找 queue_entries.status = 'revealed' AND confirm_expires_at <= now（每次最多 100 筆）。自動轉為 confirmed，將感謝小卡更新至感謝牆；重算提供者違規計數與撮合之後，才由 runInBackground 發送推播通知提供者。只有成功把狀態改為 confirmed 的那一次結算會發送推播，不會重複發送。
