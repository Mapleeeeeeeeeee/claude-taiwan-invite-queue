# 雙軌道排隊機制（Dual-Track Queue：新手專屬試用 vs 再領取）

本文件在 `invite-code-queue.md` 之後撰寫，兩者衝突時以本文件為準。被取代的規則有三條：「每個 Google 帳號終身限成功領取 1 次」改為只限新手首發軌；「已確認啟用者不能再次加入排隊」改為只限新手首發軌；「有可用名額就立即配對給排隊者」改為依軌道配對（見「撮合分配優先序」）。

## 背景與問題

平台原先採用「一人一生限領 1 次」的嚴格防刷機制。此設計雖然成功阻止單一帳號重複佔用新手體驗資源，但在社群實際運作中產生了兩大痛點：

1. **熱心提供者的排隊鎖定**：分享過邀請碼的版友（帳號已有 Pro）若想為自己的第二個測試帳號、工作分身帳號領取試用，或已領過一次的活躍版友試用期結束後想開第二個帳號時，系統一律以 `409 ALREADY_CLAIMED` 阻擋，無法排隊。
2. **提供者分享意願的細緻差異**：部分提供者希望自己的 3 個名額「專款專用」全數保留給從未體驗過 Claude Pro 的純新手；另一部分提供者則樂於無私分享給社群版友進行多帳號測試或第二帳號體驗。目前單一隊列無法滿足兩類分享者的意圖。

本功能引入「雙軌道（Dual-Track）分流機制」：提供者分享時可指定受眾偏好；排隊者可依自身狀況選擇合適軌道，兼顧「新手保障」與「再領取需求」。

---

## 使用者角色

1. **新手領取者（Newbie Receiver）**：從未在平台領取過邀請碼的 Google 帳號。核心動機是首次體驗 1 星期 Claude Pro 方案。
2. **多帳號領取者（Community Receiver）**：曾為平台提供者，或先前已成功領取過 1 次，欲為第二帳號（或朋友/工作分身）領取試用的版友。
3. **邀請碼提供者（Invite Provider）**：在 Anthropic 官方擁有 Pro 訂閱並產出 1～3 個試用額度，在平台分享時可指定該組連結的開放對象（限新手首次體驗 vs 開放再領取軌）。

---

## 需求情境

- **作為新手領取者**：當我首次來到平台時，我希望能優先配對到專門保留給新手的名額，確保不會被多帳號老手排隊擠壓，順利獲得免費試用。
- **作為曾領過／曾分享過的社群版友**：當我需要第二個 Google 帳號試用時，我希望能選擇「再領取」軌道進行排隊，而不被系統一刀切永久封鎖。
- **作為邀請碼提供者**：當我提交邀請連結時，我能明確勾選這組名額是「限新手首次體驗」還是「開放再領取軌」，讓名額流向符合我的分享心願。

## 設計意圖

1. **保護新手資源池**：透過「限新手（Newbie Track）」嚴格維持一人限領一次，確保新用戶在任何時候都不會被多開帳號的老手吃光名額。
2. **高容納度包含式撮合（Fallback Matching）**：
   - 「限新手名額」：**僅配對給新手隊列**，不可流向再領取隊列。
   - 「開放再領取軌名額」：**優先配對給再領取隊列**；若該隊列目前無人排隊，**可自動降級支援新手隊列**，避免珍貴名額閒置浪費。
3. **明示官方規則，降低無效啟用**：不具新手資格的使用者進入領取表單時，介面顯著提示「*已自動切換為再領取排隊（提醒：Claude 單一帳號無法重複試用，此名額請用於第二個帳號）*」，降低拿同一個 Pro 帳號兌換導致額度失效的機率。
4. **單一表單、自動分軌**：領取表單不提供軌道選項，系統依使用者的歷史狀態自動決定軌道，不破壞既有單頁清晰體驗。`POST /api/queue` 省略 `track` 時由系統依新手資格決定：具資格者排新手軌，其他人排再領取軌；明確帶 `track` 時照該值處理，帶 `newbie` 但不具資格仍回 409。

## 業務規則

### 詞彙定義（Ubiquitous Language）
- **新手首發軌 (`newbie`)**：面向在任何軌道都沒有已確認啟用（`confirmed`）排隊紀錄、也沒有分享過邀請連結的 Google 帳號，一人限領一次的專屬隊列。`GET /api/me` 以 `isEligibleForNewbieTrack` 回報使用者是否具備這個資格；回報無效連結後重排的次數（`invalidRetryCount`）不影響資格。
- **再領取軌 (`community`)**：面向已領取過（任一軌道有 `confirmed` 紀錄）或曾分享過邀請連結的使用者的共享隊列。這條軌道的名稱原為「第二帳號試用」，現改為「再領取軌」，看板與表單上簡稱「再領取」。Claude 單一帳號無法重複試用，所以排這條軌道的人仍須把名額用在第二個帳號，介面提示與伺服器訊息都保留這個說明。
- **軌道標籤 (`track`)**：附加於 `invite_slots`（名額）與 `queue_entries`（排隊紀錄）上的屬性，列舉值為 `newbie` 或 `community`（程式碼型別為 `QueueTrack`）。
- **票券 (`ticket`)**：撮合引擎中的排隊紀錄（`QueueEntry`）。

### 資格與權限決策表

| 使用者歷史狀態 | 可否排「新手首發軌」 | 可否排「再領取軌」 | 系統預設選擇與 UI 行為 |
| :--- | :---: | :---: | :--- |
| **純新手**（任一軌道都沒有 `confirmed`、未分享過） | 可以 | 可以（只有直接呼叫 API 才能指定，介面不提供） | 介面一律以「新手首發軌」排隊 |
| **已領過者**（任一軌道有 `confirmed`） | 不可，409 `NEWBIE_TRACK_ONLY`，訊息為「你已成功領取過新手體驗名額囉！…」 | 可以 | 自動切換為「再領取軌」並顯示提示 |
| **提供者**（分享過連結、任一軌道沒有 `confirmed`） | 不可，409 `NEWBIE_TRACK_ONLY`，訊息為「感謝你熱心分享邀請碼！…」 | 可以 | 自動切換為「再領取軌」並顯示提示 |
| **排隊中／保留中／解鎖中** | 不可，409 `ALREADY_IN_QUEUE` | 不可，409 `ALREADY_IN_QUEUE` | 同一使用者同時間僅能有 1 筆進行中排隊，不論軌道；此檢查先於新手資格檢查 |

同時領取過又分享過連結的人排新手軌時，409 `NEWBIE_TRACK_ONLY` 的訊息合併成一句，說明兩個原因；只有單一原因時使用上表的訊息。新手資格只在加入排隊的當下檢查，已經在新手軌排隊、之後才分享連結的人，他的新手票券仍可被配對。

### 撮合分配優先序（Matching Priority Rule）

當有等候中的隊列與可用席次時，撮合引擎依以下規則進行 FIFO 配對：
1. **防自我配對（Anti-Self-Matching）**：任何席次均不可配對給該席次的提供者本人（`slot.providerUserId !== ticket.userId`）。
2. **新手席次 (`slot.track === 'newbie'`)**：
   - 僅撮合給 `ticket.track === 'newbie'` 的排隊者。
   - 若新手隊列無人，該席次持續等待，**絕不**配給再領取隊列。
3. **再領取席次 (`slot.track === 'community'`)**：
   - **第一優先**：撮合給 `ticket.track === 'community'` 的排隊者，不論其優先權高低。
   - **第二優先（Fallback Matching）**：若再領取隊列無人可配，但新手隊列有等候者，撮合給 `ticket.track === 'newbie'` 的排隊者（避免名額閒置）。

新手票券加入排隊時，若池中同時有新手席次與再領取席次，先配新手席次（同一軌道內取最舊的席次），沒有新手席次才降級配再領取席次。原因是相容性是單向的：新手票券能使用再領取席次，再領取票券不能使用新手席次，所以先用自己軌道的席次，才不會讓後來的再領取票券等待、新手席次卻閒置。

同一軌道內依優先權高者先、加入時間早者先排序；回報無效後重排者的優先權為 1。優先權只在同一軌道內生效，再領取席次仍會先配給再領取隊列的票券。

## 狀態轉移

### 席次（Slot）狀態轉移
與既有狀態機相容，狀態流轉如下：
`available` → `reserved` (6hr) → `revealed` (30min) → `confirmed`；領取者回報無效時該名額為 `invalidated`。

保留逾時或領取者放棄保留時，名額回到 `available`；若同一組連結已有名額被回報無效（`invalidated`），改為 `closed`，不再開放。

### 排隊紀錄（Queue Entry）狀態轉移
`waiting` → `reserved` → `revealed` → `confirmed`。

排隊紀錄另有兩個終止狀態。保留後 6 小時未解鎖的變成 `expired`，領取者在 `waiting` 或 `reserved` 時取消的變成 `cancelled`。排隊紀錄沒有 `invalidated` 狀態；領取者回報名額無效後，紀錄回到 `waiting`，優先權設為 1 並保留原軌道，每個帳號終身限一次。

不允許的狀態轉移：
- 任一使用者在任一軌道有未結案的 `waiting`、`reserved`、`revealed` 紀錄時，禁止再次發起 `POST /api/queue`，回應 409 `ALREADY_IN_QUEUE`。
- 處於 `revealed`、`confirmed`、`expired`、`cancelled` 狀態時呼叫取消排隊，回應 409 `INVALID_STATE_TRANSITION`；使用者沒有任何排隊紀錄時回應 404 `QUEUE_ENTRY_NOT_FOUND`。

### 逾時處理
- `reserved` 滿 6 小時未解鎖：排隊紀錄變 `expired`，名額依上述規則釋出並重新撮合。
- `revealed` 滿 30 分鐘：視為已確認啟用，排隊紀錄變 `confirmed`，並推播通知提供者。
- 逾時處理在四種時機觸發：排程每 5 分鐘一次；登入狀態的 `GET /api/me`；看板快取過期後的 `GET /api/board`；加入排隊、取消、解鎖、回報無效與提交連結這幾支寫入 API。確認啟用的 API 本身不會先處理逾時。

## User Journey

### Journey 1：提供者指定受眾並發布邀請碼
1. 提供者點擊「我要分享邀請碼」。
2. 填入邀請連結、選擇可用次數（1～3 次）。
3. 選擇名額適用對象：
   - `[●] 限新手首次體驗（預設）`，說明為「保留給尚未體驗過 Pro 的版友，優先保障新手」
   - `[○] 開放再領取軌（允許已領取過者為第二帳號啟用；若無人排隊自動讓給新手）`
4. 點擊送出。系統建立該組連結，並依選擇將其下所有 slots 標記為 `newbie` 或 `community`。
5. 撮合引擎立即執行配對。

### Journey 2：純新手使用單一表單排隊
1. 未登入或純新手訪客點擊「我要排隊領取」；未登入者先以 Google 帳號登入。
2. 表單不提供軌道選項，系統以新手首發軌（`newbie`）排隊。
3. 填寫顯示暱稱與感謝小卡（5～200 字），點擊加入排隊。
4. 系統依 FIFO 自動配對 `newbie` 席次（或閒置之 `community` 席次）。

### Journey 3：已領取過的老版友為第二帳號排隊
1. 先前已領取過邀請碼的版友登入後切換至「我要排隊領取」。
2. 系統偵測到其曾有領取紀錄，排隊軌道自動切換為「再領取」，並在表單上方顯示提示：「*已自動切換為再領取排隊（提醒：Claude 單一帳號無法重複試用，此名額請用於第二個帳號）*」。
3. 版友填寫感謝小卡並送出排隊。
4. 系統建立 `track = 'community'` 之排隊票券，當有 `community` 席次時依序配對。

## 驗收標準（Acceptance Criteria）

- **AC 1（資料模型與提供端）**：提供者提交連結時若未指定 track，預設為 `newbie`；指定 `community` 時，其建立的 slots 皆標記為 `community`。
- **AC 2（排隊資格校驗）**：
  - 任一軌道已有 `confirmed` 紀錄之使用者請求加入 `newbie` 軌道時，後端回傳 409 `NEWBIE_TRACK_ONLY` 拒絕。
  - 分享過邀請連結之使用者（任一軌道沒有 `confirmed`）請求加入 `newbie` 軌道時，後端回傳 409 `NEWBIE_TRACK_ONLY` 拒絕。
  - 上述兩類使用者請求加入 `community` 軌道時，後端成功建立排隊（HTTP 201），不再拋出 `ALREADY_CLAIMED`。
  - 純新手直接呼叫 API 請求加入 `community` 軌道時，後端成功建立排隊（HTTP 201）。
  - 已有進行中排隊之使用者再次請求加入任一軌道，後端回傳 409 `ALREADY_IN_QUEUE`。
- **AC 3（撮合分流與相容）**：
  - `newbie` 席次絕不分配給 `community` 票券。
  - `community` 席次在有 `community` 票券時優先撮合給 `community`；在無 `community` 票券時可分配給 `newbie` 票券。
  - 兩軌道均嚴格遵守 `ticket.userId !== slot.providerUserId` 自我配對防護。
- **AC 4（即時名額看板）**：`GET /api/board` 回傳 `availableSlotsCount`（狀態為 `available` 的席次數）、`waitingQueueCount`（狀態為 `waiting` 的排隊數）、`totalConfirmedCount`，以及依軌道拆分的 `newbieSlotsCount`、`communitySlotsCount`、`newbieQueueCount`、`communityQueueCount`；首頁看板同時顯示總數與兩個軌道的席次數與排隊數。看板資料有 15 秒快取，期間內的數字可能落後實際狀態。`totalConfirmedCount` 另有 60 秒的獨立快取（`TOTAL_CONFIRMED_COUNT_CACHE_TTL_MS`），確認啟用時（含逾時自動確認）會清掉同一個 Worker 實例上的這份快取，所以使用者確認後下一次讀取看板就是新數字；其他 Worker 實例最多晚 60 秒才加一。獨立快取讓每次重算看板的讀取列數不會隨歷史領取數成長，才守得住 D1 每日讀取列數的額度。瀏覽器端的快取同樣是 15 秒，使用者自己的動作（加入排隊、取消、分享連結等）成功後，前端會繞過瀏覽器快取重抓看板，讓自己的動作立刻反映。
- **AC 5（前端防呆與提示）**：
  - 曾領取過者進入頁面時，表單自動以「再領取」排隊，並呈現第二帳號啟用注意事項。
  - 曾為提供者但未領取過者，表單同樣以「再領取」排隊，避免擠壓新手名額。
  - 純新手的表單沒有軌道選項，一律以新手首發軌排隊。
- **AC 6（逾時處理）**：`reserved` 滿 6 小時未解鎖，排隊紀錄變 `expired` 並釋出名額；`revealed` 滿 30 分鐘，排隊紀錄變 `confirmed`；兩者都會讓名額重新進入撮合，不必等使用者操作。
- **AC 7（回報無效後重排）**：領取者回報名額無效後，排隊紀錄回到 `waiting`、優先權為 1，且軌道與回報前相同；同一帳號第二次回報回應 409。
- **AC 8（取消）**：`waiting` 與 `reserved` 可取消，取消 `reserved` 會釋出名額並重新撮合；其他狀態回應 409 `INVALID_STATE_TRANSITION`。
- **AC 9（排隊順位）**：使用者看到的 `queuePosition` 是所有軌道合併後的 FIFO 順位（含優先權），不依軌道拆分。

## Out of Scope

- 點數/代幣交易機制（本階段不引入複雜的貢獻點數計算，維持輕量友善）。
- Claude 官方帳號真實狀態自動爬蟲檢測（系統不持有使用者 Claude 密碼，兌換規則由 UI 教育與使用者自律把關）。
