# Claude Taiwan 邀請連結排隊與感謝回饋平台（invite-code-queue）

本文件有三條規則已被 `dual-track-queue.md` 取代，兩者衝突時以後者為準。「每個 Google 帳號終身限成功領取 1 次」與「已確認啟用者不能再次加入排隊」現在只適用於新手首發軌；「有可用名額就立即配對給排隊者」現在依軌道配對。另外，下文「對寫入 API 依登入帳號與狀態限制操作頻率」目前沒有實作。

## 背景與問題
Claude Taiwan 社團近期大量出現「求邀請碼」與「發邀請碼」的貼文。常見做法是提供者直接把邀請連結貼在貼文或留言區，前三位看到的路人點進去用掉就結束了，多數人領完沒有留言道謝，後面點進去的人也只看到失效畫面。

如果不解決這個問題，會持續造成兩個後果：
1. 提供者付出名額卻拿不到任何正向回饋，分享意願逐漸降低。
2. 社團版面被大量已失效或重複求碼的貼文佔據，淹沒其他技術與應用討論。

## 使用者角色
- **提供者（Provider）**：擁有 Claude 邀請連結的社團成員，在產生邀請連結或分給朋友後還有剩餘次數時打開 App，希望能把名額分給真正需要的人並收到對方的感謝回饋。
- **領取者（Receiver）**：需要 Claude 邀請名額的社團成員，從社團置頂或宣導貼文打開 App，希望能透過公平排隊拿到可用的邀請連結，並向提供者表達謝意。

## 需求情境
- **提供者**：When 我手上有可用的 Claude 邀請連結（預設 3 次名額，或分給朋友後剩 1～2 次）想分享給社團版友，I want to 把連結交給系統自動依序分發並在對方啟用後收到手機推播感謝，so I can 確定名額有幫到人且獲得真實的回饋感，也不必自己在社團回留言管秩序。
- **領取者**：When 我需要 Claude 邀請連結但不想整天刷社團貼文搶快，I want to 透過 Google 一鍵登入加入先到先得（FIFO）排隊並開啟手機推播通知，so I can 在輪到我時直接從手機通知回來領取有效連結，並把寫好的感謝小卡送給提供者。
- **領取者（遇到失效連結）**：When 我好不容易排到並解鎖邀請連結，點開卻發現該連結已經額滿或失效，I want to 一鍵回報無效並立刻回到隊伍最前面等待下一組，so I can 不必因為提供者誤算剩餘次數而重新排隊。

## 設計意圖
- **將「邀請連結」與「邀請名額」拆開管理（預設 3 個名額，可調為 1、2、3）** → 因為 Claude 的一組邀請連結（`https://claude.ai/referral/<代碼>`）預設可供 3 人使用，且提供者可能已先分給朋友 1～2 次，允許選擇剩餘次數才能反映真實可用額度。
- **把「保留名額（6 小時內未顯示連結）」與「解鎖看碼（已顯示連結）」分成兩階段** → 因為一旦領取者看到真實連結網址，系統就無法阻止他在按「逾時」或「放棄」後私下拿去用。在還沒顯示連結前設 6 小時保留期，逾時未回來點擊解鎖就能 100% 安全地把名額讓給下一位排隊者。
- **排隊時先寫好感謝小卡，解鎖後滿 30 分鐘未回報無效即自動送出感謝** → 因為許多領取者拿到連結去註冊完 Claude 就直接關掉網頁了；預先寫好感謝小卡並搭配 30 分鐘自動確認，能保證即使領取者忘記回來按「成功啟用」，提供者依然能收到感謝推播與感謝牆小卡，且完全不需要管理員人工介入催促。
- **每個 Google 帳號終身限成功領取 1 次、無效重排限用 1 次** → 因為系統無法直接串接 Anthropic 內部資料庫查驗邀請連結是否真的被該使用者用掉，限制每帳號最多只能使用 1 次「回報無效重排最前面」，既能保護真正拿到失效連結的排隊者，又能防止惡意使用者無限白嫖。
- **任一領取者回報某組邀請連結無效時，立即停用該連結尚未發出的剩餘名額；且只要該連結曾有至少 1 人成功啟用，就不計入提供者違規** → 因為提供者常只是忘記自己已經分給幾個朋友，導致第 2 或第 3 個名額額滿；立即停用剩餘未發出名額能避免下一位排隊者也踩空，而不處罰已有成功紀錄的提供者則能避免誤傷好心人。
- **不採用前端背景高頻輪詢，改用 Web Push 推播通知搭配首頁看板快取** → 因為社團貼文曝光時可能同時有數百人打開網頁，若前端每幾秒輪詢一次狀態會迅速耗盡 Cloudflare Worker 免費版每日 10 萬次請求額度。

## 業務規則

### 名詞定義
- **邀請連結（Invite Link）**：提供者提交的 Claude 邀請網址，標準格式為 `https://claude.ai/referral/<邀請代碼>`。系統會自動擷取路徑中的 `<邀請代碼>`（忽略 `?s=ios` 等查詢參數），並將網址正規化為 `https://claude.ai/referral/<邀請代碼>`。
- **邀請代碼（Referral Code）**：邀請連結中 `/referral/` 後方的英數與連字號識別碼（例如 `rNFlbuU0OA`），作為判斷是否重複提交同一組連結的唯一依據。
- **邀請名額（Invite Slot）**：一組邀請連結可分配給領取者的獨立席次。提供者提交時預設產生 3 個邀請名額，亦可手動選為 1 個或 2 個。
- **排隊紀錄（Queue Entry）**：領取者加入等待佇列的紀錄，包含排隊順序、預寫的感謝小卡內容與目前配對狀態。
- **感謝小卡（Thank-You Card）**：領取者在加入排隊時預先填寫的一段感謝文字（5～200 字，以 Unicode 碼點計，一個 emoji 算 1 字；去掉空白與不可見字元後至少要剩一個字元），在名額確認啟用後透過 Web Push 推播給提供者，並顯示於首頁公開感謝牆。
- **完全無效連結（Completely Invalid Link）**：一組邀請連結底下所有已分配名額中，確認成功啟用數為 0，且至少有 1 個名額被領取者回報無效。

### 規則 1：邀請連結提交與驗證規則

| 條件 | 系統已存在相同邀請代碼（仍在可用／保留／已全數啟用） | 提供者累計「完全無效連結」達 2 組 | 網址格式符合 `https://claude.ai/referral/<邀請代碼>` | 選擇名額數為 1、2 或 3 | 結果 |
|------|------|------|------|------|------|
| R1-1 | 否 | 否 | 是 | 是 | 建立邀請連結與對應數量的邀請名額，並立即嘗試依 FIFO 配對排隊中的領取者 |
| R1-2 | 是 | 否 | 是 | 任意 | 拒絕提交，提示「這組邀請連結已經被分享過囉」 |
| R1-3 | 任意 | 是 | 是 | 任意 | 拒絕提交，提示「由於先前提供的連結多次被回報無效，目前已暫停提供權限」（已被暫停的提供者重複提交既有代碼時也回這則，避免他用重複提交探測哪些代碼已被分享） |
| R1-4 | 任意 | 任意 | 否 | 任意 | 拒絕提交，提示「請貼上正確的 Claude 邀請連結（格式如 https://claude.ai/referral/...）」 |

**實例**：
- 提供者小明貼上 `https://claude.ai/referral/rNFlbuU0OA?s=ios`，選擇可用次數 `3`（預設），系統正規化為 `https://claude.ai/referral/rNFlbuU0OA` 並擷取代碼 `rNFlbuU0OA`，建立 3 個「可用（Available）」邀請名額。
- 5 分鐘後另一位使用者貼上 `https://claude.ai/referral/rNFlbuU0OA`（無 `?s=ios`），系統比對邀請代碼同為 `rNFlbuU0OA`，拒絕提交並提示已分享過。

### 規則 2：FIFO 配對與 6 小時保留規則

| 觸發時機 | 目前是否有「可用（Available）」邀請名額 | 目前是否有「排隊中（Waiting）」領取者 | 結果 |
|------|------|------|------|
| 提供者新增邀請連結（含 N 個名額） | 是（剛新增 N 個） | 是（假設有 M 人排隊） | 依排隊時間先後，將前 `min(N, M)` 個名額配對給前 `min(N, M)` 位排隊者，狀態轉為「已保留待解鎖（Reserved）」，設定保留到期時間為當前時間 + 6 小時，並發送 Web Push 推播給獲配的領取者 |
| 提供者新增邀請連結 | 是 | 否（0 人排隊） | N 個名額維持「可用（Available）」留在池中等待未來的領取者 |
| 領取者送出感謝小卡加入排隊 | 是（池中至少有 1 個可用名額） | 否（自己即為第 1 順位） | 立即配對最早建立的 1 個可用名額，直接進入「已保留待解鎖（Reserved）」狀態，領取者在畫面上可立即點擊解鎖看碼 |
| 領取者送出感謝小卡加入排隊 | 否（池中 0 個可用名額） | 任意 | 進入「排隊中（Waiting）」狀態，顯示目前排隊順位 |
| 系統定時檢查（或讀取時觸發）發現「已保留待解鎖」超過 6 小時 | - | 隊伍中有其他排隊中領取者 | 原領取者的排隊紀錄轉為「逾時取消（Expired）」（該領取者可重新點擊排隊，排到隊伍最後）；該邀請名額立即轉配給目前隊伍最前面的排隊者並發送推播 |
| 系統定時檢查（或讀取時觸發）發現「已保留待解鎖」超過 6 小時 | - | 隊伍中無其他排隊中領取者 | 原領取者的排隊紀錄轉為「逾時取消（Expired）」；該邀請名額退回「可用（Available）」狀態 |

**實例**：
- 佇列中有小華（10:00 排隊）、小美（10:05 排隊）共 2 人。提供者小張在 10:10 分享 1 組預設 3 次的邀請連結，系統立即將名額 #1 配給小華、名額 #2 配給小美（保留至 16:10），並發推播給兩人；名額 #3 維持「可用」。
- 小華在 16:11 仍未打開 App 解鎖，系統將小華標記為「逾時取消」，名額 #1 釋出給下一位排隊者。

### 規則 3：解鎖看碼、感謝回饋與無效重排規則

| 領取者動作 / 時間條件 | 解鎖後是否未滿 30 分鐘 | 該帳號歷史「回報無效重排」次數 | 結果 |
|------|------|------|------|
| 在 6 小時保留期內點擊「解鎖查看邀請連結」 | - | - | 顯示完整邀請連結網址與複製按鈕，名額與排隊紀錄轉為「已解鎖待確認（Revealed）」，確認截止時間設為當前時間 + 30 分鐘 |
| 解鎖後點擊「成功啟用，送出感謝 ❤️」 | 任意 | 任意 | 名額與排隊紀錄轉為「已確認啟用（Confirmed）」，立即發送 Web Push 推播感謝小卡給提供者，並將感謝小卡刊登於首頁公開感謝牆 |
| 解鎖後滿 30 分鐘未點擊任何按鈕 | 否（已滿 30 分鐘） | 任意 | 系統自動將名額與排隊紀錄轉為「已確認啟用（Confirmed）」，發送 Web Push 推播感謝小卡給提供者，並刊登於首頁公開感謝牆 |
| 解鎖後點擊「邀請連結無效／已額滿 ⚠️」 | 是（30 分鐘內） | 0 次（尚未使用過重排機會） | 1. 該邀請名額轉為「回報無效（Invalidated）」<br>2. 同一組邀請連結底下其餘尚未發出的「可用（Available）」名額一併轉為「因同組無效而停用（Closed）」（已配對給他人的名額不受影響）<br>3. 該領取者的無效重排次數 +1，排隊紀錄回到「排隊中（Waiting）」且優先順序排在所有一般排隊者最前面（若池中還有其他連結的可用名額則立即配對） |
| 解鎖後點擊「邀請連結無效／已額滿 ⚠️」 | 是（30 分鐘內） | 已達 1 次（已用完終身 1 次機會） | 介面不開放無效重排（按鈕顯示已用完重排額度並停用），名額視為已領取完畢 |
| 解鎖後超過 30 分鐘才想點無效 | 否（已逾 30 分鐘） | 任意 | 該名額已自動轉為「已確認啟用（Confirmed）」，不可再回報無效 |

**實例**：
- 小美在 10:15 點擊解鎖看到 `https://claude.ai/referral/rNFlbuU0OA`，打開註冊成功後忘了回來按確認。10:45（滿 30 分鐘）系統自動將該名額標記為「已確認啟用」，把小美預寫的「謝謝小張大大分享！」推播給小張，並放上公開感謝牆。
- 阿明拿到小陳分享的連結（3 個名額中的第 1 個），在解鎖後 5 分鐘內發現連結已失效，點擊「邀請連結無效／已額滿 ⚠️」。系統將名額 #1 標為「回報無效」，同時把小陳這組連結還沒發出去的名額 #2、#3 標為「因同組無效而停用」，並將阿明排回隊伍第 1 順位。

### 規則 4：帳號領取上限與提供者防濫用規則
- **領取上限**：每個 Google 帳號只要有 1 筆排隊紀錄處於「排隊中」、「已保留待解鎖」、「已解鎖待確認」或「已確認啟用」，就不能再次加入排隊。只有處於「逾時取消」或「主動取消排隊」時才可重新加入隊伍尾端。
- **自己不能領自己提供的連結**：若提供者自己也在排隊中，配對邏輯會跳過提供者本人的排隊紀錄。
- **提供者防濫用判定**：當一組邀請連結的所有名額都已結束（無「可用」、「已保留待解鎖」或「已解鎖待確認」名額），若該連結底下「已確認啟用」名額數為 `0` 且「回報無效」名額數 `>= 1`，該連結計為 1 組「完全無效連結」。同一提供者累計達 2 組「完全無效連結」時，禁止再提交新連結；但若該連結曾有至少 1 人「已確認啟用」（代表只是剩餘次數估算誤差），則不計入違規。

## 狀態

### 邀請名額（Invite Slot）的狀態

| 狀態 | 事件 | 誰能觸發 | 條件 | 轉移後 | 使用者看到 |
|------|------|---------|------|--------|-----------|
| 可用（Available） | 配對給排隊者 | 系統（新連結建立、新排隊者加入、或前一位逾時釋出時） | 佇列中有等待中的領取者（且非提供者本人） | 已保留待解鎖（Reserved） | 領取者收到推播，畫面顯示「已為你保留名額，請於 6 小時內解鎖」 |
| 可用（Available） | 同組連結有其他名額被回報無效 | 領取者（回報同組另一名額無效） | 同屬一組邀請連結 | 因同組無效而停用（Closed） | 首頁可用名額數減少；提供者看到該連結剩餘未發出名額已停用 |
| 已保留待解鎖（Reserved） | 點擊「解鎖查看邀請連結」 | 領取者 | 未超過 6 小時保留期限 | 已解鎖待確認（Revealed） | 顯示完整邀請連結、複製按鈕，以及「成功啟用 ❤️」「邀請連結無效 ⚠️」按鈕 |
| 已保留待解鎖（Reserved） | 超過 6 小時未解鎖 | 系統（定時任務或請求時檢查） | 當前時間 > 保留到期時間 | 可用（Available）（並立即嘗試配給下一位排隊者） | 原領取者畫面顯示「保留已逾時，名額已讓給下一位版友，可重新排隊」 |
| 已保留待解鎖（Reserved） | 點擊「放棄並取消排隊」 | 領取者 | 尚未解鎖看碼 | 可用（Available）（並立即嘗試配給下一位排隊者） | 領取者回到未排隊狀態；名額配給下一位 |
| 已解鎖待確認（Revealed） | 點擊「成功啟用，送出感謝 ❤️」 | 領取者 | 未超過 30 分鐘確認期 | 已確認啟用（Confirmed） | 領取者看到「已送出感謝卡給提供者！」；提供者收到推播通知；感謝牆新增小卡 |
| 已解鎖待確認（Revealed） | 解鎖滿 30 分鐘未操作 | 系統（定時任務或請求時檢查） | 當前時間 > 解鎖後 30 分鐘 | 已確認啟用（Confirmed） | 系統自動送出感謝卡推播給提供者並刊登於感謝牆 |
| 已解鎖待確認（Revealed） | 點擊「邀請連結無效／已額滿 ⚠️」 | 領取者 | 解鎖未滿 30 分鐘，且該領取者無效重排次數 = 0 | 回報無效（Invalidated） | 領取者看到「已為你排回隊伍最前面，將優先為你配對下一組」 |

不允許的轉移：
- `已解鎖待確認（Revealed）` → `可用（Available）`：不允許，因為邀請連結網址已經曝光給該名領取者，不能再將同一個名額退回池中當作全新名額重複計算，畫面不提供「退回名額」選項。
- `已確認啟用（Confirmed）` → `回報無效（Invalidated）`：不允許，使用者看到「此名額已完成啟用與感謝回饋，無法再變更狀態」。
- `回報無效（Invalidated）` → 任何其他狀態：不允許，已作廢名額不可恢復。

### 排隊紀錄（Queue Entry）的狀態

| 狀態 | 事件 | 誰能觸發 | 條件 | 轉移後 | 使用者看到 |
|------|------|---------|------|--------|-----------|
| 排隊中（Waiting） | 系統配對到可用名額 | 系統 | 為隊伍最前順位且有非本人提供的可用名額 | 已保留待解鎖（Reserved） | 收到手機推播，畫面切換為倒數 6 小時的「解鎖查看邀請連結」卡片 |
| 排隊中（Waiting） | 點擊「取消排隊」 | 領取者 | 處於排隊中 | 已取消（Cancelled） | 顯示「已取消排隊」，可隨時重新排隊 |
| 已保留待解鎖（Reserved） | 點擊「解鎖查看邀請連結」 | 領取者 | 6 小時保留期內 | 已解鎖待確認（Revealed） | 顯示邀請連結網址與 30 分鐘確認倒數 |
| 已保留待解鎖（Reserved） | 超過 6 小時未解鎖 | 系統 | 逾時 | 逾時取消（Expired） | 顯示「名額保留已逾時，若仍需要請重新加入排隊」 |
| 已保留待解鎖（Reserved） | 點擊「放棄名額」 | 領取者 | 尚未解鎖 | 已取消（Cancelled） | 顯示「已放棄名額並取消排隊」 |
| 已解鎖待確認（Revealed） | 點擊「成功啟用」或滿 30 分鐘 | 領取者 / 系統 | - | 已確認啟用（Confirmed） | 顯示「恭喜成功領取！你的感謝小卡已送達提供者」與先前領到的連結備查 |
| 已解鎖待確認（Revealed） | 點擊「邀請連結無效／已額滿 ⚠️」 | 領取者 | 30 分鐘內且無效重排次數 = 0 | 排隊中（Waiting，具最高優先權重） | 顯示「已為你優先排回隊伍最前面（剩餘重排機會 0 次）」，若池中有其他可用名額則立即配對 |

不允許的轉移：
- `已確認啟用（Confirmed）` → `排隊中（Waiting）`：不允許，每個 Google 帳號限成功領取一次，畫面顯示「你已經成功領取過邀請連結囉！歡迎未來有邀請碼時回來分享給其他版友」。

## User Journey

### Journey 1：領取者排隊、收到推播、解鎖連結並送出感謝
入口：使用者從 Claude Taiwan Facebook 社團貼文點擊連結打開 PWA 網頁（或從手機主畫面打開已安裝的 PWA）。
前置條件：使用者尚未登入，且未曾成功領取過邀請連結。

1. 使用者打開首頁 → 畫面顯示即時看板（目前可用名額數、目前排隊人數、累計已分享人數）、公開感謝牆，以及「我要排隊領取」與「我要分享邀請碼」兩個主區塊。
2. 使用者點擊畫面上的 Google 官方登入按鈕 → 在彈出視窗選擇 Google 帳號，完成後留在首頁，顯示使用者名稱。
3. 若使用 iPhone 且尚未將網頁加入主畫面，畫面頂部顯示簡短引導卡片：「iPhone 用戶請點下方『分享』→『加入主畫面』，排到邀請碼時才能收到手機推播通知喔！」；若已在 PWA 或 Android／桌面瀏覽器，顯示「點此開啟推播通知」按鈕 → 使用者點擊並允許通知權限，系統完成 Web Push 訂閱綁定。
4. 使用者在「我要排隊領取」區塊輸入自己的顯示暱稱（預設帶入 Google 顯示名稱，可修改；留空時使用帳號既有暱稱；不可為空、最多 50 字（以 UTF-16 長度計，與感謝小卡的碼點計數不同）、去掉空白與不可見字元後至少要剩一個字元；已建立的帳號重新登入時，不會被 Google 顯示名稱覆蓋）與「給提供者的感謝小卡」（例如：「謝謝好心版友分享！祝你寫 code 都不會遇到 bug！」），點擊「加入排隊」 →
   - 若池中已有可用名額：直接跳至步驟 6（立即進入「已保留待解鎖」狀態）。
   - 若池中無可用名額：畫面顯示「排隊成功！你目前在第 X 順位，輪到你時會發送手機推播通知」。
5. 當有提供者分享新連結且輪到該使用者時 → 使用者手機收到 Web Push 推播通知：「🎉 輪到你領取 Claude 邀請碼囉！請在 6 小時內點擊解鎖，逾時將自動讓給下一位版友」。
6. 使用者點擊推播通知打開 App，看到「名額已為你保留（剩餘 05:59:xx）」與「解鎖查看邀請連結」按鈕，並點擊該按鈕 → 畫面顯示完整連結 `https://claude.ai/referral/rNFlbuU0OA`、「一鍵複製連結」與「直接前往連結」按鈕，下方出現「成功啟用，送出感謝 ❤️」與「邀請連結無效／已額滿 ⚠️（30 分鐘內有效）」兩顆按鈕。
   → 先點解鎖才顯示網址，確保未回來的人不會看到網址，逾時才能安全讓給下一位。
7. 使用者點擊前往連結並在 Claude 網站完成使用，回到 App 點擊「成功啟用，送出感謝 ❤️」 →
   - 畫面顯示「🎉 感謝小卡已送達提供者！」。
   - 首頁公開感謝牆立即出現這張感謝小卡（顯示領取者暱稱、提供者暱稱、感謝內容與時間）。
   - 提供者的手機立即收到 Web Push 推播通知：「💌 你分享的邀請碼幫助了 [領取者暱稱]！對方留言：『謝謝好心版友分享！...』」。

### Journey 2：提供者分享邀請連結並收到 3 位版友的感謝推播
入口：擁有 Claude 邀請連結的社團成員打開 PWA 網頁並完成 Google 登入。
前置條件：提供者手上有 1 組 `https://claude.ai/referral/rNFlbuU0OA?s=ios` 邀請連結。

1. 提供者切換至「我要分享邀請碼」分頁，看到提示說明：「一組 Claude 邀請連結預設可給 3 個人使用；若你已經先分給朋友，可調整剩餘可用次數」。
2. 提供者貼上 `https://claude.ai/referral/rNFlbuU0OA?s=ios`，確認「剩餘可用次數」為預設的 `3 次`、確認自己的顯示暱稱，並點擊「送出分享（並開啟感謝通知）」 →
   - 若尚未開啟 Web Push 推播，系統順勢請求推播權限，讓提供者能收到感謝通知。
   - 系統驗證格式並正規化為 `https://claude.ai/referral/rNFlbuU0OA`，建立 3 個邀請名額，立即配對給目前排隊中的前 3 位領取者（不足 3 人則先配給現有排隊者，剩餘名額留在可用池）。
   - 畫面顯示分享成功與這組連結底下 3 個名額的即時狀態（例如：名額 #1 已保留給版友、名額 #2 已保留給版友、名額 #3 等待排隊者中）。
3. 當領取者點擊「成功啟用，送出感謝 ❤️」（或解鎖滿 30 分鐘自動確認）時 → 提供者手機收到 Web Push 推播通知，點開 App 可在「我的分享紀錄」中看到自己分享的連結已幫助了幾個人，以及每個人寫給他的感謝小卡。

## 替代流程
- **領取者解鎖後忘記回來按「成功啟用」**：領取者在 Journey 1 步驟 6 點擊解鎖看碼後，直接去用掉邀請碼並關閉網頁。解鎖滿 30 分鐘後，系統自動將該名額轉為「已確認啟用」，把排隊時預寫的感謝小卡推播給提供者並放上感謝牆，提供者完全不會因為領取者忘記按按鈕而少收到回饋。
- **領取者遇到無效／已額滿連結並一鍵重排**：領取者在 Journey 1 步驟 6 點擊解鎖後，點開 Claude 網頁發現顯示該邀請連結已額滿或失效。領取者在 30 分鐘內回到 App 點擊「邀請連結無效／已額滿 ⚠️」，系統立即將該名額標記無效、關閉同一組連結尚未發出的剩餘名額，並將該名領取者排回隊伍第 1 順位（若池中還有其他提供者的可用名額，當場直接配給他新的一組）。
- **領取者排到名額但超過 6 小時未解鎖**：系統在 6 小時到期後自動將該名額回收並配給下一位排隊者；原領取者下次打開 App 時看到「保留已逾時」，可點擊「重新加入排隊」排到隊伍尾端。
- **使用者不開啟或裝置不支援 Web Push 推播**：開啟推播為強烈建議但非強制阻斷；若使用者略過推播設定，仍可正常排隊與分享，只是需自行打開網頁查看是否輪到自己。

## 錯誤情境

### 系統錯誤
- **配對或狀態更新時發生資料庫寫入失敗**：所有配對、解鎖、回報無效操作皆在資料庫交易（Transaction / Batch）內完成；若中途失敗，名額與排隊紀錄維持原狀態，畫面提示「系統忙碌中，請稍後再試一次」，不會發生「名額被扣掉但沒配給任何人」或「兩個人同時搶到同一個名額」的狀況。
- **Web Push 推播發送失敗（例如使用者移除 PWA 或推播憑證過期）**：推播發送失敗不影響名額配對與感謝小卡上牆；若推播服務回傳憑證已失效（HTTP 404/410），系統自動清除該筆失效的推播訂閱紀錄。

### 使用者誤操作
- **提供者貼上整段包含說明文字的句子**（例如：「這是我的邀請碼 https://claude.ai/referral/rNFlbuU0OA?s=ios 拿去用吧」）：系統自動從文字中擷取 `https://claude.ai/referral/<邀請代碼>` 網址，不必強迫使用者手動刪頭去尾；若整段文字完全不包含合法的 Claude referral 網址，才提示格式錯誤。
- **領取者不小心按到「邀請連結無效／已額滿 ⚠️」**：因為每帳號終身只有 1 次無效重排機會，點擊「邀請連結無效／已額滿 ⚠️」時會彈出二次確認對話框：「確定這組邀請連結無法使用嗎？回報後將為你優先重排下一組（每個帳號僅限使用 1 次無效重排機會）」，確認後才送出。

### 惡意行為
- **領取者拿到有效連結用完後，故意按「邀請連結無效」想多拿第 2 組送朋友**：每個 Google 帳號終身最多只能觸發 1 次無效重排，第 2 次領到的名額畫面不再開放無效重排，把損失嚴格鎖死在最多 1 次，且不需人工介入審判。
- **惡意使用者亂貼假連結（格式正確但代碼是亂編的）**：當該組連結的第 1 位領取者回報無效時，該組連結剩下的 2 個可用名額會立刻自動關閉，不會再害到第 2、第 3 位排隊者；且同一帳號累計 2 組「完全無效連結」即自動封鎖提供權限。
- **短時間大量請求刷 API**：不依賴前端高頻輪詢，首頁公開看板資料加上短暫快取（Cache），並對寫入 API 依登入帳號與狀態限制操作頻率。

## Out of Scope
- 不串接 Anthropic 非公開 API 自動驗證邀請碼是否還有剩餘額度（Anthropic 無公開此 API，且私自爬蟲易遭 Cloudflare 阻擋）。
- 不建立管理員人工審核爭議後台（所有逾時回收、無效重排、自動感謝與違規停權皆由規則自動執行）。
- 不提供 Email 或簡訊通知（統一使用免費且原生的 PWA Web Push）。
- 不支援單一 Google 帳號重複領取多組已確認啟用的邀請連結。

## 整合點
- **部署與執行環境**：Cloudflare Workers（結合 Assets 提供前端 PWA 靜態資源與後端 API）。
- **資料庫**：Cloudflare D1（SQLite），負責儲存使用者、邀請連結、邀請名額、排隊紀錄、感謝小卡與 Web Push 訂閱資訊。
- **排程任務**：Cloudflare Workers Cron Triggers，定期執行「6 小時未解鎖逾時回收並轉配下一位」與「解鎖滿 30 分鐘自動確認並發送感謝推播」（同時在 API 讀取/操作時也會即時觸發檢查，確保零延遲）。
- **身分驗證**：Google OAuth 2.0 / Google Identity Services 一鍵登入。
- **推播通知**：Web Push Protocol（VAPID），支援 Android Chrome、桌面瀏覽器與 iOS 16.4+ 加入主畫面的 PWA。

## 規模與預期壽命
- **預估規模**：屬於 Claude Taiwan 社團專用中小型工具，日常同時排隊人數約數十至數百人，社團貼文剛發佈時可能有數百至上千人次瀏覽首頁。
- **資源約束**：必須穩定運作於 Cloudflare Workers（每日 10 萬次請求）與 D1（每日 500 萬列讀取、10 萬列寫入）免費方案額度內。因此嚴格禁止前端背景短間隔輪詢（Polling），狀態更新以「使用者打開/操作時讀取 + Web Push 推播通知喚醒 + 首頁公開統計快取」為主。
- **預期壽命**：社團長期輕量維運工具，需做到「零人工客服／零人工排障」自動化運作。

## Acceptance Criteria

- **AC 1（提供者提交連結與自動正規化）**
  Given 使用者已透過 Google 登入
  When 在分享區塊貼上包含 `https://claude.ai/referral/rNFlbuU0OA?s=ios` 的文字並維持預設可用次數 3 次送出
  Then 系統將連結正規化為 `https://claude.ai/referral/rNFlbuU0OA`、建立 3 個邀請名額，且若再次貼上相同邀請代碼（不論有無 `?s=` 參數）會被拒絕並提示已分享過

- **AC 2（提供者自訂剩餘可用次數）**
  Given 使用者已透過 Google 登入且手上的連結已先分給朋友用掉 1 次
  When 貼上邀請連結並將「剩餘可用次數」調整為 2 次後送出
  Then 系統僅為該組連結建立 2 個邀請名額，最多只會分配給 2 位排隊者

- **AC 3（FIFO 自動配對與即時推播）**
  Given 隊伍中有 2 位領取者正在排隊（依序為 A 與 B），且目前池中無可用名額
  When 提供者提交 1 組含 3 個名額的邀請連結
  Then A 與 B 立即依序獲配名額 #1 與名額 #2（狀態轉為「已保留待解鎖」，保留期限 6 小時）並收到 Web Push 推播通知，而名額 #3 維持「可用」留在池中

- **AC 4（池中有碼時排隊即刻獲配）**
  Given 目前池中還有至少 1 個「可用」邀請名額（非該領取者本人提供）
  When 新領取者填寫感謝小卡並點擊「加入排隊」
  Then 不需等待，畫面直接進入「已保留待解鎖」狀態，領取者可立即點擊「解鎖查看邀請連結」

- **AC 5（6 小時未解鎖逾時安全回收）**
  Given 領取者 A 已獲配名額處於「已保留待解鎖」狀態（尚未看到邀請連結網址），且隊伍後方有領取者 B 正在排隊
  When 超過 6 小時領取者 A 仍未點擊「解鎖查看邀請連結」
  Then 領取者 A 的排隊紀錄轉為「逾時取消」，該名額自動轉配給領取者 B 並發送推播通知給 B

- **AC 6（解鎖後手動確認啟用與感謝推播）**
  Given 領取者已在 6 小時內點擊「解鎖查看邀請連結」並看到完整網址
  When 領取者點擊「成功啟用，送出感謝 ❤️」
  Then 該名額與排隊紀錄轉為「已確認啟用」，提供者收到包含該領取者感謝小卡的 Web Push 推播通知，且首頁公開感謝牆顯示該張感謝小卡

- **AC 7（解鎖滿 30 分鐘未操作自動確認並送出感謝）**
  Given 領取者已點擊「解鎖查看邀請連結」看到完整網址，但之後關閉網頁未點擊任何按鈕
  When 解鎖時間滿 30 分鐘
  Then 系統自動將該名額與排隊紀錄轉為「已確認啟用」，自動發送感謝小卡推播給提供者並刊登於首頁公開感謝牆

- **AC 8（遇到無效／額滿連結時回報無效、優先重排與連動停用剩餘名額）**
  Given 一組邀請連結共有 3 個名額（名額 #1 已解鎖、名額 #2 與 #3 仍為尚未配出的「可用」狀態），且領取者 A 尚未使用過無效重排機會
  When 領取者 A 在解鎖後 30 分鐘內點擊「邀請連結無效／已額滿 ⚠️」並確認
  Then 名額 #1 轉為「回報無效」，同組連結尚未配出的名額 #2 與 #3 立即轉為「因同組無效而停用」不再分給其他人，且領取者 A 排回隊伍最前面（優先獲配下一組其他提供者的可用名額），其剩餘無效重排機會變為 0 次

- **AC 9（限制每帳號終身最多 1 次無效重排與 1 次成功領取）**
  Given 領取者 A 已經使用過 1 次「回報無效重排」並獲配第 2 組邀請名額
  When 領取者 A 解鎖第 2 組邀請名額
  Then 畫面上的無效重排按鈕為停用狀態（顯示已用完 1 次重排機會），且當名額轉為「已確認啟用」後，該帳號無法再次加入排隊

- **AC 10（提供者違規門檻與好心人保護）**
  Given 提供者 P 分享的第 1 組連結有 2 人成功啟用、第 3 人回報無效（因提供者記錯剩餘次數）
  When 系統計算提供者 P 的違規紀錄
  Then 由於該連結曾有至少 1 人成功啟用，不計入「完全無效連結」，提供者 P 仍可繼續分享；唯有當提供者累計 2 組連結皆為「0 人成功啟用且被回報無效」時，才禁止其再次提交連結
